# フロントエンド(画面の構成と幅への対応)

本書は instant-news の画面がどう組み立てられ、どの幅で何が変わるのかを説明する。実装は `server/web/`(ページの HTML、`css/style.css`、`js/api.js`、`js/chrome.js`、`js/admin.js`、`js/theme.js`)と、それらを配信する `server/app/pages.py` にある。本書とこれらは常に一致させる。

ページごとの経路と HTML の対応は [docs/api.md](api.md) の「ページ」節が持つ。画像の変種(`orig` / `1200w` / `400w`)の生成と配信は [docs/media.md](media.md) が持つ。本書はそれらを画面がどう使うかだけを述べる。

## ビルドを持たない

フロントエンドは素の HTML / JavaScript / CSS であり、変換も束ね込みも行わない。`server/app/pages.py` が HTML をそのまま返し、`server/main.py` が `/static/css` と `/static/js` を静的配信する。JavaScript は ES モジュールとして閲覧器が直接読む。

この選択の代償は、モジュールの解決が閲覧器に見えるパス(`/static/js/api.js`)そのものであることと、依存を足せないことである。得ているのは、画面を直すのにビルド環境が要らないことと、配信されているものと書いたものが同一であることの 2 つ。報道の場である以上、表示されている内容が何に由来するのかを追える方が重要である。

## 画面の層は 3 つに分かれる

| 層 | 担当 | 実体 |
| --- | --- | --- |
| HTTP | 取得・JSON・ID の文字列化・画像 URL の組み立て | `js/api.js` |
| DOM の共通部品 | ヘッダ・ナビ・ドロワー・利用者やタグの断片 | `js/chrome.js` |
| ページ固有 | そのページだけの取得と描画 | 各 HTML の `<script type="module">` |

ID は全ての層で文字列として扱う。Discord のスノーフレークは 64 ビットであり、数値化すると下位桁が黙って壊れる。

`js/chrome.js` に集約したものをページへ写し取らない。写し取られたものは食い違う。実際に起きた例が 2 つある。1 つは利用者のアバターで、4 つのページが存在しない `user.avatar_url` を参照していたために一度も実画像を出せていなかった。もう 1 つはナビの機能系導線で、トップだけが タグ・連載・記事を書く の 3 つを持ち、残る 6 ページは 記事を書く だけを持っていた。どちらも「同じものを 2 度書いた」ことの帰結である。

## 幅は 3 層で扱う

デスクトップの規則を土台に、狭い方へ 2 段階で上書きする。

| 層 | 幅 | 何が変わるか |
| --- | --- | --- |
| デスクトップ | 901px 以上 | 本来の 2 段組(メイン + サイドバー 300px)。 |
| タブレット | 900px 以下 | サイドバーをメイン列の下へ畳む。検索欄は白帯に残す。タブレットの縦(768〜834px)がここに入る。 |
| スマホ | 600px 以下 | 白帯を ロゴ + 🔍 🌙 ☰ へ、青帯をカテゴリ専用へ削る。降ろした導線はドロワーが引き取る。 |

境目を 600px に置いたのは、iPhone・Android の縦がいずれも 360〜430px に収まり、横向きは 640px 以上になるためである。600px はこの 2 つの間の空白にあり、どちらの実機にも境目が掛からない。タブレットの縦は 768px 以上であるため、900px の層に留まる。

メディアクエリは末尾へまとめず、上書きする規則の直後に置く。まとめると、デスクトップ側の値を変えた者の目に狭幅側の値が入らず、両者が食い違ったまま気付かれない。

## 段には min-width: 0 が要る

`.layout` の段(`.main` / `.side`)には `min-width: 0` を与える。grid の項目は既定で `min-width: auto` を持ち、これは「中身の min-content より狭くならない」を意味する。縮められない中身がその段にあると、段はその幅まで広がり、`.container` の `max-width: 100%` を突き抜けてページ全体を横に流す。

縮められない中身は現に複数ある。API キーのスコープ(`articles:write:any`)、Discord のロール ID(19 桁の数字)、執筆者が書いた本文中の表。これらは途中で折り返せない 1 語である。

したがってこれは調整ではなく前提である。これが無いと、内側に `overflow-x` の枠を置いても枠自身が広がってしまい、何も起きない。

## 横スクロールは枠の内側に閉じ込める

桁を削れない表は、ページごと横に流すのではなく、表だけを横スクロールさせる。

- **API キーの一覧・分類の一覧** … `.table-scroll` で包む(`settings.html` の `data-keys` / `data-subs`、`js/admin.js` の分類パネル)。狭幅では表を `width: max-content` にして、縮められない桁が潰し合うのを防ぐ。
- **本文中の表** … `.prose table` を 900px 以下で `display: block` + `overflow-x: auto` にする。桁数を決めるのは執筆者であり、こちらで制御できない。ラッパ要素は使えない。本文の HTML は `server/app/markdown.py` が nh3 で許可要素だけへ削り込んでおり、`div` も `class` 属性も許可一覧に無いためである。見た目のために許可を広げると、その属性を経由した注入を検討する必要が生まれる。
- **カテゴリの帯** … `.globalnav .container` が `overflow-x: auto`。カテゴリはデプロイごとに数が異なり、狭幅では必ず溢れる。

デスクトップは対象にしない。表を `display: block` にすると内容幅へ縮み、桁の少ない表が段の幅いっぱいに広がらなくなる。

## スマホのナビはカテゴリを帯に残す

青帯はカテゴリ専用にし、機能系の導線(タグ・連載・管理・記事を書く)とアカウント欄(利用者名・ログアウト・設定)はドロワー(☰)へ移す。

カテゴリを畳まないのは、それが記事の主分類であり、読者が最も多く使う導線だからである。数が可変でドロワーに畳むと、辿るのに常に 2 タップ掛かる。帯に残して横スクロールで辿らせ、続きがあることは端のフェード(`js/chrome.js` の `mountNavFade`)で示す。幅が足りているときはフェードを付けない。続きが無いのにあるように見せないためである。

ドロワーと青帯は `js/chrome.js` の `utilLinks` という 1 つの一覧から描く。描く先が 2 つに増える以上、出どころを 1 つにしないと食い違いは倍に増える。

ドロワーは 601px 以上では存在ごと消す(`display: none`)。閉じているだけにすると、広い画面で Tab を送った利用者が見えない導線の中へ潜り込む。開いている間は焦点をドロワーの中に閉じ込め、Esc と背景の押下で閉じ、閉じたら元の焦点へ返す。

## 検索はスマホでだけ畳む

検索欄は 600px 以下でのみ 🔍 の押下まで畳む。601px 以上では常設する。

以前はこれを 900px 以下で一律に隠していた。しかし 768px の端末はロゴ(約 320px)とアカウント欄(約 78px)を引いてなお 340px が残り、入る幅がある。入るのに畳むと、`/?q=` の結果を開いた読者が、何で絞ったのかを見ることも直すこともできないまま「「◯◯」の検索結果」だけを見せられる。

検索語を伴って開かれたページでは、スマホでも初めから開く。同じ理由による。

## 一覧では 400w を引く

一覧・カード・サムネイル・ロゴ・タグのアイコンは `api.js` の `mediaVariant(url, '400w')` を通す。記事面(本文中の画像)と og:image は原寸のままとする。変種の一覧と生成の規則は [docs/media.md](media.md) が持つ。

`mediaVariant` は `/media/{64 桁の 16 進}/{変種}.webp` の形に当たる URL だけを読み替え、それ以外はそのまま返す。カバー・報道社のロゴ・タグのアイコンは自由書式の列であり、取り込みを経ない外部ホストの絶対 URL がそのまま入りうる(カバーは API から任意の URL を入れられ、ロゴとアイコンは管理画面で手入力する)。外部の URL に変種の名前を継ぎ足せば、当然そこには何も無い。

変種が実在しなくてよい。原寸より広い変種は生成されず、アニメーションは `orig` しか持たないが、配信側は変種を見つけられなければ `orig` を返す(`server/app/routers/media.py` の `_read_variant`)。したがって「400w を要求する」は「400px 以下で足りる。あるならそれをくれ」を意味し、無い場合に壊れることはない。

## 指の的は 44px、チップは 36px

単独で立つ操作(ボタン・ページャ・ドロワーの項目・ヘッダのアイコン)は 44px(`--tap`)にする。34px は指の腹より小さく、隣を巻き込んで押してしまう。

チップ(タグ雲・記事末尾のタグ)は 36px に留める。タグ雲は 1 つの面に数十個が並ぶため、全てを 44px にすると雲だけで画面が埋まり、探している当のタグが視界から消える。押し間違いは的の大きさだけでなく的の間隔でも決まるため、高さを抑えて隙間を広げる。36px は WCAG 2.2 の下限(24px)を余裕をもって超える。

的を大きくするのはリンクそのものであって、リンクを含む行ではない。行に余白を足しても、その余白を叩いた指はどこへも行かない。1 行に収まる見出し(順位の一覧・連載・年表)は 20px 前後にしかならないため、リンク自身を `display: block` にして上下の余白を持たせる。

一覧の行(`.article-row`)は行全体をリンクにしない。タイトルだけが記事へのリンクで、報道社・カテゴリ・タグはそれぞれの一覧ページ(報道社ページ・カテゴリ・タグページ)への個別のリンクを持つ。行全体を 1 つのリンクにすると、行の中に別のリンクを入れられず(リンクの入れ子は不正な HTML)、これらの導線が押せなくなる。タイトルは見出しであり行の高さで足りるため広げない。報道社・カテゴリ・タグはメタ行に密に並ぶチップであり、44px へ広げると一覧が間延びして一画面に入る記事が減るため、チップのまま(隙間で押し間違いを防ぐ扱い)に留める。

## 入力欄は 16px にする

600px 以下では入力欄の文字を 16px にする。iOS の Safari は 16px 未満の入力欄へ焦点が移った瞬間にページを拡大し、拡大は戻らない。拡大された状態では横スクロールが生まれ、以降どの画面も横に流れる。狭幅で「なぜか画面がずれる」と感じられる原因の多くはこれであり、レイアウトの問題ではない。

## エディタは狭幅で並びを組み替える

デスクトップのエディタは 本文 | 公開設定 の 2 段組であり、設定は本文の右にあって常に見えている。狭幅で段組を畳むと、この右列がまるごと本文の下へ落ちる。本文の入力欄は最低でも 240px あり、その下に 5 枚のカードが続くため、カテゴリ(必須)にも「公開」にも、書き終えて長く送った先でしか出会わない。

そこで 600px 以下では 見出し → 公開設定 → 閲覧範囲 → カバー画像 → 速報・広告 → 本文 → 公開 の順へ組み替える。書く前に必須項目が目に入り、書き終えた先に公開がある。

実装は `.main` と `.side` を `display: contents` にしてカードを直接の項目へ引き上げ、`order` で並べる。2 段組を保ったまま順序だけを変える方法は他に無い(`order` は同じ親の中でしか効かず、カードは `.main` と `.side` に分かれている)。順序は各カードの class(`ed-head` / `ed-body` / `ed-publishing` / `ed-visibility` / `ed-cover` / `ed-promo` / `ed-publish`)で指定する。位置を `nth-child` で数えると、カードを 1 枚足しただけで順序が黙って崩れる。

記事の識別(見出し・リード文)と本文が別のカードなのはこのためである。両者の間に公開設定が挟まるため、1 枚には収められない。

## 一覧のメタ行はスマホでタグを降ろす

一覧の 1 行には 報道社・カテゴリ・タグ・記者・コメント数・点数・閲覧範囲・日時 が並ぶ。狭幅ではこれが見出しより背が高くなるため、タグのチップだけを降ろす。

タグを選んだのは、それが他の入口(記事ページのタグ行・タグの一覧)から辿れるのに対し、報道社と閲覧範囲はここにしか出ないためである。

開示(`.badge.sponsored`)と速報は降ろさない。広告が見出しと見分けられない状態は、記事の信頼性を直接損なう。これは装飾ではなく要件である。

## 配色はライト/ダークの両対応

OS の設定(`prefers-color-scheme`)に従い、`data-theme` 属性による手動トグル(`js/theme.js`)がそれを上書きする。`theme.js` はモジュールではなく `<head>` で同期的に読む。保存されたテーマを描画前に適用し、既定テーマで一瞬描画されてから切り替わるのを避けるためである。

同じ色の一覧が `@media (prefers-color-scheme: dark)` と `:root[data-theme="dark"]` の 2 箇所に現れるのは、メディアクエリと属性セレクタを 1 つの規則にまとめられないためである。
